2) Sincronización:
En cada caso decidir si están bien utilizadas las primitivas de sincronización y justificar.

    a) Usar un spin lock para hacer acceso exclusivo a disco.
    b) Usar un semáforo binario para incrementar un contador.

    a)
    Un spinlock (TAS) garantiza exclusión mutua, pero lo hace con busy waiting, es decir, el proceso espera activamente mientras el recurso está ocupado.

    En el caso del acceso a disco (especialmente si es HDD con alto tiempo de acceso), el tiempo de espera puede ser muy largo.

        - si el disco está atendiendo otra petición y el proceso debe esperar varios milisegundos (latencia física del disco, scheduling tipo elevador).

    Durante ese tiempo, el spinlock mantiene al CPU ocupado sin hacer trabajo útil, lo que degrada el rendimiento.

    En su lugar, es mejor usar un semáforo (binario) que bloquee al proceso y lo pase a estado waiting, liberando el CPU para otros procesos.

    b)

    Depende de si se dispone de operaciones atómicas.

    Si el incremento del contador se puede hacer con una operación atómica como getAndInc(), entonces no es necesario un semáforo. 
    La operación es indivisible y segura para concurrencia.
    
    Si no se dispone de tipos atómicos, entonces sí se requiere una primitiva de sincronización y podríamos usar un semáforo binario o mutex.

3) Memoria:
Te daban un arbolito de procesos y te mostraba las paginas que tenía mapeadas cada uno, pedía explicar porque motivo ciertas páginas pertenecían a 
varios procesos.
    El árbol era algo así:
    100 -> 101 -> 102
    100 -> 103
    Y las páginas eran:
    100 {A, B, C}
    101 {A, D, E}
    102 {F, B, C}
    103 {A, B, C}

    Se me ocurren 3 razones principales:

        1. Copy-On-Write (COW):

            - Al hacer un fork(), el hijo hereda el espacio de direcciones del padre.
            - Para optimizar, ambos procesos comparten inicialmente las mismas páginas físicas marcadas como solo lectura.
            - Si alguno intenta escribir, se produce un page fault, y el SO crea una copia privada de la página.

            Es probable que las páginas A, B y C estén siendo compartidas por COW.

        2. Bibliotecas compartidas (Shared Libraries):

            - Páginas como A pueden contener código de bibliotecas dinámicas (por ejemplo, libc.so), que se cargan solo una vez en memoria.
            - Estas bibliotecas se mapean en todos los procesos que las usan como read-only, por lo que se pueden compartir sin conflicto.
            - Esta es otra razón por la cual varios procesos pueden tener la página A.


        3. Memoria compartida explícita (Shared Memory / IPC)

            - El sistema puede permitir regiones de memoria mapeadas explícitamente entre procesos distintos, por ejemplo con shmget() y mmap().
            - Esto es útil para mecanismos de IPC (Inter-Process Communication).
            - En este caso, las páginas B o C podrían representar una región compartida usada para comunicarse entre procesos.
            - En este contexto, es fundamental el uso de sincronización (mutex, semáforos) para evitar condiciones de carrera.
        

4) Sistema de Archivos:
Hablaba de un volumen lógico con discos físicos y se quería hacer el funcionamiento de RAID 0+1 y RAID 5. Preguntaba cuantos discos eran necesarios para 
hacer funcionar cada uno y explicar en palabras cada método y que configuraciones había que hacerles.

RAID 0+1 (Stripping + Mirroring) Es una combinación de RAID 0 y RAID 1:

    Primero se aplica RAID 0: se divide la información en bloques y se escribe en paralelo en múltiples discos (stripping), lo que mejora el 
    rendimiento de lectura y escritura.

    Luego se aplica RAID 1: se genera una copia espejo exacta de los discos (mirroring) en otros discos. Mejora la lectura pero la escritura
    puede llegar a tomar desde el mismo tiempo hasta el doble.

    Configuración mínima:

        - Dos pares de discos: un RAID 0 (mínimo 2 discos) replicado con RAID 1 (otros 2 discos).
        - En total: 4 discos (mínimo).

RAID 5 (Stripping con paridad distribuida):

    RAID 5 distribuye datos y paridad (información redundante) entre todos los discos del arreglo.

    En cada conjunto de bloques:

        - N-1 discos contienen datos.
        - 1 disco contiene un bloque de paridad (se rota entre los discos).
        - La paridad permite reconstruir la información si falla un solo disco.

    Configuración mínima:

        Se necesita al menos 3 discos para implementar RAID 5:

            - 2 para datos.

            - 1 para paridad (la paridad rota, no está fija pero se entiende).

    a) El proceso corre con max privilegio en un contenedor.

       vunerabilidades del kernel.

    b) Las VMs usan sus propios kernels, sistemas operativos y hay mecanismos de aislamiento de HW para que no usen más de lo que deben.
       Que tengan privilegios máximos en esto es mucho mejor que en contendor ya que el aislamiento de HW les va a dificultar salir.
       Me parece que es la más segura ya es muy complicado que pueda tomar control del host o del hipervisor.

    c) Estos son como los de las guías, Me parece que es el menos seguro. Como en la guía pueden intentar subir su nivel de privilegios y romper todos
       Es el menos seguro.
